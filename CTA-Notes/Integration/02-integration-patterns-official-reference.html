Canonical deep-dive on the six Salesforce integration patterns, rebuilt against the current Salesforce Architects guide. This is the vocabulary the board expects — use these exact pattern names when presenting, and be ready to defend the fit ranking (Best / Good / Suboptimal) of the mechanism you picked.

How the official doc is structured

Every pattern follows the same template: Name → Context → Problem → Forces → Solution → Sketch → Results → Sidebars → Example. In a board, the Forces are your clarifying questions and the Solution fit table is your justification. Reciting Context and Sketch wins no points; naming the force that drove your choice does.

1. Three integration categories

Classify before you choose a mechanism. Examiners probe whether you understand why the data is moving, not just how.

CategoryThe requirementPatterns
Process IntegrationA business process spans two or more applications. Usually long-running, stateful, needs orchestration and compensating/rollback logic on failure.Remote Process Invocation (Request & Reply, Fire & Forget), Remote Call-In
Data IntegrationTwo or more systems must hold timely, meaningful, consistent data. No business logic invoked — this is synchronisation.Batch Data Synchronisation, Remote Call-In, UI Update Based on Data Changes
Virtual IntegrationA user must view, search, or modify data that stays in the external system. No copy, no reconciliation.Data Virtualisation

The most common mis-classification

“Sync the ERP order into Salesforce so reps can see it” is often not Data Integration — if reps only read it and it must be real-time, it’s Virtual Integration and you should not be storing it at all. Ask about reporting, sharing, and offline needs to decide: those three requirements are what push you from Data Virtualisation back to replication.

Key CTA exam point

Inbound calls to Salesforce are always synchronous request-reply at the transport level. There is no inbound async API. “Asynchronous inbound” is simulated either by the caller discarding the response, or by the caller publishing a platform event so Salesforce-side processing is decoupled. Bulk API 2.0 is the exception in spirit: the job is processed asynchronously, but the submission call itself is synchronous.

3. Remote Process Invocation — Request and Reply

Type / TimingProcess (or Data) / Synchronous
DirectionSalesforce → remote
ProblemAn event in Salesforce must start a remote process, pass data, receive a response, and track state from it — all in one transaction.
Volume profileSmall, real-time, single-record (a few hundred at most).

Forces to ask about: Must Salesforce wait before continuing? Must the response be processed in the same transaction? Message size? Is the trigger a UI action or a DML event? Can the endpoint respond with low latency, and how many users will do this at peak?

Solution fit

SolutionFitWhy
External Services invokes a REST API declarativelyBestNo code. Requires an OpenAPI 2.0/3.0 (or YAML) schema; primitive types plus nested objects and header params supported. Invocable from Flow. See External Services.
LWC/Aura/page → Apex REST or SOAP callout (use a Continuation if latency risk)BestFull control; WSDL2Apex generates a proxy class for SOAP. Continuations avoid burning synchronous Apex governor limits on slow endpoints.
HTTP Callout action in FlowGoodDeclarative sync REST from Flow with no Apex and no OpenAPI spec required. The pragmatic middle ground when External Services doesn’t fit.
Trigger → async Apex calloutSuboptimalAll callouts from trigger context must be async, so you can’t reply into the same transaction. This is really the Fire-and-Forget pattern.
Batch Apex → sync calloutSuboptimalWorks, but callout limits apply per execution context (~200-record chunks). Not a real-time pattern.

Sidebars that get challenged

  • Timeliness: Apex callout timeout is configurable up to 120 seconds; the doc recommends setting it to 5 seconds. Mitigate the org limit of 50 concurrent long-running (>5s) synchronous transactions — blow through it and unrelated users start failing. This is the number to quote when someone proposes a chatty sync callout on a high-traffic page.
  • Error handling: the caller owns it. Show the user an actionable message.
  • Recovery: nothing commits in Salesforce until a successful response is received, so the retry is naturally safe on the Salesforce side.
  • Idempotency: the remote procedure must be idempotent. Standard mechanism — the consumer sends a unique message/correlation ID and the receiver tracks duplicates. Creates in the remote system must check for duplicates first, keyed on a unique Salesforce ID. If the call originates from the UI, handle idempotency at the integration layer (middleware), not in the browser.
  • State management: either Salesforce stores the remote surrogate key (use an External ID field — available in the same transaction because this is synchronous), or the remote system stores the Salesforce record ID.
  • Security: one-way SSL by default; two-way SSL/mTLS supported with self-signed or CA-signed certs (Mutual TLS (2-Way SSL)); use Named Credentials (Named Credentials) and OAuth 2.0 (OAuth 2.0 Flows); Apex Crypto for hashes and digital signatures (cryptography).
  • WS-Security is not natively supported — inject headers via a security/XML gateway (preferred) or hand-code them via WSDL2Apex (not recommended).

Official example: a utility company creates a billing account in an external system during ordering. Consume the billing HTTP API via External Services or Flow HTTP Callout (use an Apex proxy only for SOAP), store the returned account number on the Salesforce account to track state.

4. Remote Process Invocation — Fire and Forget

Type / TimingProcess / Asynchronous
DirectionSalesforce → remote
ProblemStart a remote process and pass data without waiting; the remote side acknowledges receipt and hands control straight back.

Forces to ask about: Is guaranteed delivery required? Is the message small? Can the remote system participate in contract-first integration where Salesforce owns the contract? Does the endpoint/ESB support long polling (CometD) or gRPC (Pub/Sub)? Are declarative methods preferred over Apex?

Solution fit

SolutionFitWhy
Flow-driven platform eventsBestDeclarative publish on insert/update. Many subscribers, zero coupling. Platform Event-Triggered Flows let you build the listener declaratively too. See Platform Events & Change Data Capture.
Pub/Sub APIBestThe recommended way for external consumers to subscribe (and publish). gRPC + HTTP/2, OAuth/JWT/session auth. See Sub API.
Change Data CaptureBestFully declarative, publishes create/update/delete/undelete change events. Right choice when the trigger really is “any record change”.
Event RelayBest (AWS)Serverless, low-code streaming of platform events and CDC straight to Amazon EventBridge — no integration app to write, and events can flow back.
OmniStudio Integration ProceduresGoodDeclarative server-side orchestration: multiple actions in one server call, transformations, caching. No user interaction.
Apex-driven platform eventsGoodSame bus, but published from Apex when you need logic the Flow can’t express.
Flow-driven outbound messagingSuboptimalLegacy. SOAP, contract-first, retries until positive ack (a form of guaranteed delivery). New builds must use Flow + platform events.
LWC → async Apex calloutSuboptimalCustomisation, and you must code guaranteed delivery.
Apex trigger / batch → async calloutSuboptimalWorks, but limits per execution context and no built-in durability.

Sidebars that get challenged

  • Publishing behaviour — the classic gotcha.
SettingBehaviourChoose when
Publish After CommitEvent published only if the transaction commitsSubscribers will read records the publishing transaction created/changed
Publish ImmediatelyPublished when the publish call runs, ignoring rollbackYou want the event regardless of outcome (e.g. logging, audit, error signalling)
  • Idempotency / reliable messaging: platform events are published to the bus once — Salesforce does not retry. It is the subscriber/ESB’s job to request replay via Replay ID. Messages are retained for 72 hours. Design the subscriber to be an idempotent receiver (dedupe on a correlation ID).
  • CDC gap events: when Salesforce cannot generate a change event it sends a gap event instead (header carries the change type, e.g. GAP_CREATE). Overflow events signal that more than the allowed number of changes happened in one transaction. A robust subscriber must handle both — this is a favourite QA question.
  • Error handling: with events, the subscriber owns error handling — the event is handed off. Failed flows email the admin (and Flow_Interviews / paused interviews); events are not retried by the platform on the publish side.
  • State management: because the process is async, storing the remote key requires a callback into Salesforce (that callback is the Remote Call-In pattern).
  • Limits: 100,000 events/hour standard-volume, 250,000/hour high-volume (usage-based), 1 MB max message size. See governor-limits-and-best-practices.

Official example: telco converts a Close-Won opportunity to an order. Flow publishes a platform event; the ESB subscribes via Pub/Sub API, forwards to the ERP, then calls back with OAuth 2.0 + a connected app to write the order number onto the opportunity. Demonstrates async invocation, end-to-end guaranteed delivery, and a callback for state.

5. Batch Data Synchronisation

Type / TimingData / Asynchronous, scheduled
DirectionBoth
ProblemImport into and export out of Salesforce in bulk without interfering with end users.

Forces to ask about: Should the data even be stored in Salesforce (if not → Data Virtualisation)? Event-driven refresh or scheduled? Does it support a primary business process? Are there reporting requirements that depend on it being local?

Solution fit

SolutionFitData masterWhy
Third-party ETL (MuleSoft, Informatica) with CDC on the sourceBestRemoteTool detects source changes, transforms, calls Bulk API 2.0. Use REST if volumes are small.
Third-party ETL driving off Salesforce timestampsGoodSalesforceQuery by SystemModstamp/status to filter the target set; extract via Bulk API 2.0 or REST.
Data 360 actions & activationsBestData 360Sync between orgs after ingestion — especially strong for Marketing Cloud.
Data 360 + Data Graphs + Connect APIBestData 360MuleSoft Anypoint extracts via Connect/Data Graph API and moves to another org.
Composite Graph APIBestSalesforceUp to 75 graphs per payload, 500 nodes per graph (REST v50+). Great for related multi-object writes. See Composite API.
Data Import Wizard / Data LoaderFitEitherFine for stewardship and one-offs; not an integration strategy.
Remote call-in as the syncSuboptimalRemoteContinuous chatter, heavy error handling and locking, user-facing performance risk.
Remote process invocation as the syncSuboptimalSalesforceSame objection in reverse.

The ETL control-table (watermark) design — say this out loud in a board

The official pattern is explicit, and it is what separates a real answer from “we’ll use MuleSoft”:

  1. Implement change data capture on the source data set.
  2. Keep control tables in an intermediate database the ETL tool owns.
  3. Each run: read the control table for the last successful run timestamp, use it as the extract filter, apply validation/enrichment, write to Salesforce, then update the watermark on success — or write restart values and exit on failure.

Salesforce is the spoke, not the hub

Put the control tables somewhere the ETL tool can reach even when Salesforce is unavailable. The ETL infrastructure is the hub.

Other must-mention practices: chain/sequence jobs; match on primary keys from both systems (External IDs); extract only changed data; group child records by parent key before loading to avoid UNABLE_TO_LOCK_ROW; make post-import triggers process selectively; and for volume, follow ldv-best-practices and calculating-data-storage.

Sidebars that get challenged

  • Timeliness: design to a batch window. Loading during business hours causes contention — a user update fails, or worse a partial batch fails. For 24/7 global orgs a window may not exist: use data segmentation (record types, filter criteria) to avoid contention.
  • State management: surrogate keys both ways. If you need transactional integrity across objects, don’t use batch — use Remote Call-In with Apex.
  • Optimistic locking: Salesforce holds no edit state. It records the read time; on save it checks whether someone else updated the row and forces the user to re-read.
  • Middleware must support Bulk API and must persist the last successfully processed timestamp (watermarking) internally or externally.
  • Error handling: on read, retry non-infrastructure errors and log/terminate/notify via control+error tables. On write, use the per-record result set (record ID, success/failure, error collection) to drive selective retries.

Official example: a mainframe nightly job assigns prospects to reps; an ETL tool detects the source changes and loads them into Salesforce via the REST API.

6. Remote Call-In

Type / TimingProcess or Data / Synchronous (always, at transport level)
DirectionRemote → Salesforce
ProblemHow does a remote system connect, authenticate, notify Salesforce of external events, and create/update records?

Forces to ask about: Is this an event notification (EDA — publisher decoupled from consumer) or CRUD on specific records? One object per transaction or several related ones? SOAP or REST? Message size? Can the remote system do contract-first (Salesforce supplies the WSDL)? Is transaction processing required? How much customisation in Salesforce are you willing to tolerate?

Solution fit

SolutionFitWhy
Composite APIBestUp to 25 subrequests in one call, referencing each other’s results. Cuts round trips and API consumption.
Composite Graph APIBest75 graphs / 500 nodes; each graph succeeds or fails as a unit.
REST APIBestPublish events, query (incl. Named Query), CRUD, describe metadata. See REST API.
Bulk API 2.0Best for bulkREST-based async insert/upsert/query/delete. Anything > 2,000 records belongs here.
GraphQL APIBestSuperior to REST for complex multi-object reads with selective fields. See GraphQL API.
Pub/Sub APIBestThe recommended way for external systems to publish onto the event bus (gRPC, OAuth/JWT/session).
Platform Events via APIBestPublishing is just POST /services/data/vXX.X/sobjects/Event__e/. Decouples the remote caller from Salesforce-side logic.
SOAP APISuboptimalOnly when the client can’t do REST, or contract-first is mandated. See SOAP API.
Apex web services (webservice / SOAP)SuboptimalChoose only for full transactional support across objects or custom logic on the way in. Each service has its own WSDL — code-first, so the contract only exists after you build it.
Apex REST services (@RestResource)SuboptimalSame reasoning without WSDL/stub generation. Composite resources can give you multi-update in one transaction.

Why "Best" APIs beat "Suboptimal" custom Apex services

Custom Apex services are ranked lower not because they’re bad, but because they put transformation, orchestration and error handling inside Salesforce where they cost maintenance and governor limits. The doc’s line: those concerns belong in middleware. Only reach for Apex REST/SOAP services when you need multi-object transactional atomicity or custom pre/post logic the standard APIs can’t express.

Sidebars that get challenged

  • Data volumes: SOAP/REST create/update/delete handle 200 records per call (call repeatedly for more). > 2,000 records → Bulk API 2.0. Queries return up to 2,000 rows before queryMore.
  • Governor limits: API request caps are per 24 hours, by edition × licence count (e.g. Unlimited Edition allows 5,000 requests per Platform licence per 24h). Platform events: 100k/hr standard, 250k/hr high-volume, 1 MB max message.
  • Timeliness: session timeout per org setting; SOQL query timeout is 120 seconds.
  • Security: the platform enforces the logged-in (integration) user’s profile, sharing and permission sets — so design that user deliberately, with API-only access. Add profile IP restrictions. TLS 1.2+ with ≥128-bit ciphers. Establish an OAuth trust, and cache and reuse the access token rather than re-authenticating per call. See oauth-saml-flows-and-iam and data-security.
  • Idempotency: the remote system (or middleware) must manage duplicate calls on timeout/retry — otherwise you get duplicate inserts and duplicate downstream automation.
  • Reliable messaging: REST/SOAP are synchronous with no WS-ReliableMessaging. The remote system must implement retry. With platform events, subscribers can use Replay ID within the 72-hour window.
  • Complex scenarios: aggregation, orchestration, transformation cannot be done by SOAP/REST API — middleware, preferably.

Official example: an on-premises Printer Management System pushes ink/paper levels. Salesforce defines a platform event; the PMS authenticates (OAuth web-server or bearer) and publishes the event via SOAP/REST API; a Flow subscriber updates the asset and creates an order. Platform events were chosen because the number of subscribers is variable and non-finite — for simple updates to a known set of records, plain SOAP/REST would do.

7. UI Update Based on Data Changes

Type / TimingData / Asynchronous (near real time)
DirectionSalesforce → Salesforce UI
ProblemNotify the user in the Salesforce UI without a refresh and without losing their work.

Forces to ask about: Does the data need to be stored in Salesforce? Can a custom UI layer be built? Will the user have access to invoke it?

Solution

Platform events are the recommended solution — structured payload independent of any object, durable topic with a 72-hour replay window so a consumer that comes online late still gets the message. Moving parts:

  • an Apex trigger or Flow that publishes the event,
  • the topic/channel,
  • Pub/Sub API (gRPC + HTTP/2) for efficient consumption by external clients,
  • a Lightning web component subscribing via lightning/empApi,
  • a JavaScript library as a static resource (for CometD-era implementations).

Limits you must volunteer

BenefitUnsupported requirement
No custom polling mechanism neededDelivery is not guaranteed
No user-initiated refresh loopOrder is not guaranteed
Bulk API record changes do not generate notifications

The Bulk API blind spot

If the upstream process loads data with Bulk API, the UI will not light up. This single line has sunk otherwise-good board answers where a nightly bulk load was expected to drive a live agent console.

Official example: telco managers want to know when a rep closes a case successfully. Apex trigger publishes an event on Status = Closed + Resolution = Successful; a custom UI subscribes (Pub/Sub API / empApi) and shows alerts filtered to that manager’s reps.

8. Data Virtualisation

Type / TimingVirtual / Synchronous
DirectionRemote → Salesforce, on demand
ProblemView, search and modify external data without moving it into Salesforce.

Forces to ask about: Do you want declarative/point-and-click or a UI mashup? Is the data set too large to copy? Do you only need small amounts at a time? Is real-time accuracy required? Are there data residency constraints?

Solution fit

SolutionFitWhy
Salesforce Connect (external objects)BestMaps external tables to external objects (__x). Adapters: OData 2.0/4.0, cross-org, custom Apex (Apex Connector Framework). No storage consumed, no sync. See Salesforce Connect & External Objects.
Data 360 + Zero CopyBestSync via connectors/APIs/MuleSoft, or reference data with zero copy, then use the OOTB integrations from Data 360.
Data 360 + Data Cloud OneBestHarmonise via the Customer 360 Data Model, identity resolution and data federation into one customer view.
Request & Reply (custom page/button → Apex callout, or a mashup/Canvas app)SuboptimalWorks for narrow read-only views; you own the UI, error handling and caching. Justify it on cost when Salesforce Connect can’t be licensed.

External object relationships — memorise this table

RelationshipAllowed childAllowed parentMatched on
LookupStandard, Custom, ExternalStandard, Custom18-character Salesforce record ID
External lookupStandard, Custom, ExternalExternalThe External ID standard field
Indirect lookupExternal onlyStandard, CustomA custom field marked External ID and Unique

Sidebars that get challenged

  • No record-level sharing on external objects. Access to the object means access to every row. If row-level security is a requirement, Data Virtualisation via external objects is out — say so before the examiner does.
  • Timeliness: configurable 120-second max wait for the external system. Users are waiting, so this pattern is small-volume real-time only — never batch payloads.
  • Rate limits: OData adapters have hourly callout caps. If you hit them, enable High Data Volume on the external data source to bypass most rate limits (accepting its own behaviours/limitations). Reports over external objects are the usual culprit.
  • Paging: choose server-driven or client-driven paging via the Server Driven Pagination field on the external data source.
  • CSRF: OData 2.0/4.0 external data sources have specific CSRF behaviours to review.
  • Validation: the Salesforce Connect Validator is a free tool for shaking out common query failures.
  • Compatibility: external objects behave like custom objects but a long list of features doesn’t apply (and report performance suffers) — cite the considerations docs.

Official example: manufacturer’s service agents need live ERP order data. Configure an OData external data source (directly or through middleware — Boomi, Informatica, Jitterbit, MuleSoft and Progress all ship adapters), sync tables to external objects, and Salesforce Connect makes the real-time callout when the page loads.

9. Cross-pattern decision cheatsheet

If the requirement says…PatternFirst-choice mechanism
”must show the result to the user immediately”Request & ReplyExternal Services / Flow HTTP Callout / Apex + Continuation
”notify the downstream system when X happens”Fire & ForgetFlow → platform event; Pub/Sub API subscriber
”any change to the record must flow out”Fire & ForgetCDC (declarative, no payload design)
“stream events to AWS”Fire & ForgetEvent Relay → EventBridge
”nightly / weekly load of millions of rows”Batch Data SyncETL + Bulk API 2.0 + watermark control tables
”ERP pushes order status into Salesforce”Remote Call-InREST/Composite API, or publish a platform event
”external system needs 25 related writes atomically”Remote Call-InComposite Graph API (or Apex REST for true cross-object transactions)
“agent’s screen must update live”UI UpdatePlatform event + LWC empApi
”don’t copy the data — show it live”Data VirtualisationSalesforce Connect (OData / cross-org / Apex adapter)
“unified profile across many sources”VirtualData 360 (+ Zero Copy / Data Cloud One)

Board discipline

Name the pattern, name the mechanism, then immediately give volume, timing, authentication, error handling and idempotency. Every pattern above has an error-handling and an idempotency sidebar for a reason — those are the two topics QA reliably returns to.
