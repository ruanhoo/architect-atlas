(OAuth Authorization Flows)

Overview

Salesforce supports multiple OAuth 2.0 flows. Choosing the right one depends on: who is authenticating (user vs server), whether a browser is available, and the security requirements.

Web Server Flow (Authorization Code)

(Web Server Flow)

1. App redirects user → Salesforce authorization endpoint
2. User logs in and approves
3. Salesforce returns authorization code to redirect URI
4. App exchanges code for access_token + refresh_token
5. App uses access_token for API calls
  • Most secure for user-context apps — code never exposed to browser
  • Supports MFA enforcement
  • Refresh token allows long-lived sessions without re-login
  • Use for: Web apps, Experience Cloud integrations, partner apps

JWT Bearer Flow

(JWT Bearer Flow)

1. App creates JWT signed with private key (client cert)
2. POST to token endpoint with grant_type=urn:ietf:params:oauth:grant-type:jwt-bearer
3. Salesforce validates JWT signature against registered certificate
4. Returns access_token (no refresh token)
  • No user interaction — fully automated
  • Certificate-based — private key never leaves the app server
  • No refresh token — must re-request access token when expired (short-lived: ~1–2 hours)
  • Use for: Server-to-server integrations, CI/CD pipelines, Named Credentials, Pub/Sub API

CTA default for server-to-server

JWT Bearer is the recommended flow for any server-to-server integration. It’s secure (no client secret in URL), supports automation, and is compatible with Named Credentials External Credentials.

Client Credentials Flow

(Client Credentials Flow)

1. App POSTs client_id + client_secret to token endpoint
2. Salesforce returns access_token
  • No user context — runs as a connected app (or designated user)
  • Simpler than JWT Bearer but uses a shared secret (less secure than certificate)
  • Must enable in Connected App settings; assign a “Run As” user
  • Use for: M2M integrations where certificate management is not feasible

Warning

Client secret must be stored securely (e.g. Named Credentials, secrets manager). Never hardcode in application code.

Device Flow

(Device Flow)

1. Device requests a device_code and user_code from Salesforce
2. User visits a URL on a separate device and enters user_code
3. Device polls Salesforce until user approves
4. Salesforce returns access_token + refresh_token
  • For devices with no browser or limited input (CLI, IoT, TV apps)
  • Salesforce CLI uses this flow for sf org login device
  • Use for: CLI tools, kiosk apps, headless servers where a human needs to authenticate once

Username-Password Flow

  • App POSTs username + password + security token directly to token endpoint
  • Returns access_token immediately
  • Avoid in production:
    • Bypasses MFA enforcement
    • Credentials sent in plaintext over HTTPS (no browser redirect)
    • Salesforce may block if IP restriction policies are active
  • Acceptable for: Development, Postman testing, sandbox automation where MFA is not enforced

Implicit (User-Agent) Flow

  • Returns access_token directly in URL fragment after browser redirect
  • Token exposed in browser history and logs
  • No refresh token
  • Deprecated for most uses — use Web Server flow for SPAs instead
  • Only kept for specific legacy use cases

Connected App Configuration

(Connected App Setup)

Every OAuth integration requires a Connected App:

  • Define allowed OAuth scopes (api, refresh_token, web, etc.)
  • Set callback URL for Web Server flow
  • Upload certificate for JWT Bearer flow
  • Enable Client Credentials flow (opt-in)
  • Configure IP relaxation and refresh token policy
