What Counts as LDV

No hard threshold — context-dependent.

Not an official citation

The LDV Best Practices Guide — Introduction only defines LDV loosely (“tens of thousands of users, tens of millions of records, or hundreds of GB of storage”); it does not state the per-object-type thresholds below. Those are practitioner/community guidelines (unverified against an official Salesforce source as of 2026-09-23) — treat them as rules of thumb, not exam-quotable facts.

Object typeIndicative threshold
Standard/custom objects> 1 million records
Chatter / Feed items> 5 million records
ContentDocument / Files> 500k records
Sharing table (e.g. AccountShare)> 10 million rows

Salesforce recommends staying well under ~50 million records per object. At or near that scale, you must plan offload/archive.

CTA framing

Examiners expect you to proactively raise LDV concerns whenever a scenario involves high-volume transactional data, migrations, or sharing rule proliferation — not just when explicitly stated. Call out any object likely to hit 1M+ records; at 50M+, archiving/offload is mandatory in the design.

Experience Cloud + Account/Contact LDV

If LDV is on Account and/or Contact records tied to Experience Cloud users, do not casually archive them. Prefer monitoring for account/ownership skew and performance issues, and use custom indexes and skinny tables if slowdowns appear. Archiving contacts linked to community users is risky unless absolutely required.

Why LDV Causes Problems

Verification status

The intro page cited below only defines LDV loosely — it does not itemize these problems. Each bullet’s verification status is noted; treat “not verified”/“inference” items as things to double-check before quoting on the exam, not as confirmed facts.

  • Full table scans when indexes are absent or not selective (plausible — well-established platform behavior, but not confirmed against a specific quoted source)
  • Sharing recalculation becomes long-running → lock contention (not verified — source page renders client-side only; couldn’t confirm exact claim)
  • Report timeouts (10-minute limit) (not verified — no specific limits source located)
  • Batch Apex chunking inefficiency (plausible — batch size/scope trade-offs are real, but “chunking inefficiency” is paraphrased, not a quoted claim)
  • SOQL governor limits hit faster on unindexed queries (inference — reasonable derived consequence, not something the guide states directly)
  • Search index lag (confirmed — Search Architecture: “it could take about 15 minutes or more for the updated text to become searchable”)

Data Skew

Skew is the #1 LDV interview topic. Three types (the “Data Skew” article this cited — sf.performance_data_skew.htm — no longer appears in Salesforce’s current Help sitemap; no live replacement found as of 2026-09-23, likely retired/folded into the LDV Best Practices Guide):

Ownership Skew

One user/queue owns a disproportionate number of records (e.g. integration user owns 500k Accounts). Practical risk often starts around > ~10k records owned by a single user.

Impact: A skewed-ownership user moving roles or being added to/removed from a public group used by a sharing rule triggers a long-running recalculation of access rights across that user’s owned records. (Avoid Ownership Skew / Group Membership Skew)

Fix:

  • Use multiple integration/owner users to distribute ownership (no single user crosses the ~10k-record danger zone, so no one user’s role/group change triggers a large recalculation)
  • Use a dedicated “data owner” user per business unit (isolates skew to a stable, rarely-moved account rather than a real user who might change roles or teams)
  • Avoid assigning a role to a skewed-ownership user at all, if possible (no role membership means no role-hierarchy-implied sharing to recalculate in the first place)
  • If a role is unavoidable, place that user in a separate role at the top of the role hierarchy, never move them out of it, and keep them out of public groups used as sharing-rule sources (a top-level role has no parent to cascade into, and never moving the user or changing their groups means the recalculation trigger never fires)
  • If private OWD is required, prefer criteria-based sharing rules over role-hierarchy-implied access — criteria-based rules don’t recalculate when a skewed-ownership user’s role/group membership changes, avoiding that specific trigger (not a general claim that private OWD beats public — Public Read/Write still avoids sharing computation entirely and is the stronger fix when recalculation cost itself, not just the role-move trigger, is the problem; see W during load)

Lookup Skew (Parent Skew) / Account Skew

Many child records point to the same parent (e.g. 100k Cases linked to one Account). Account skew is the common CTA case: > ~10k child records under a single Account can cause record locking and sharing issues. (Avoid Account Data Skew)

Root cause: This is a general lookup-relationship behavior, not specific to Account as parent or to master-detail relationships. On every insert/update, Salesforce must lock the target record(s) each lookup field points to, on any object, to maintain referential integrity — so whichever record has many children looked-up to it becomes a lock bottleneck under heavy concurrent insert/update activity. Account is the common example (and the CTA exam case) simply because it’s the most frequently over-referenced parent object in practice. (Managing Lookup Skew to Avoid Record Lock Exceptions)

Impact: Lock contention on the parent during concurrent child insert/update → “unable to lock row”; sharing recalculation pain.

Fix: Four mitigation categories, per Managing Lookup Skew to Avoid Record Lock Exceptions:

  1. Reducing record save time — shorten how long the lock is held:
    • Avoid locking the parent in triggers on the child (don’t update parent aggregate fields synchronously)
    • Use Platform Events or async processing to defer parent updates (Platform Events Developer Guide)
    • Redesign aggregation; use roll-up summaries carefully
    • Consolidate to a single trigger per object and move non-critical logic off the synchronous path (source: Managing Lookup Skew blog)
  2. Distributing the skew — reduce concentration on any one target record:
    • For Account skew: distribute children across multiple parent accounts where the data model allows
    • Add more distinct lookup values instead of concentrating records on one target, and prefer leaving a lookup blank over pointing everything at a generic “catch-all” record (source: same blog)
  3. Using a picklist field — if the field has a small, fixed set of lookup values, use a picklist instead of a lookup; picklists don’t require record locks (source: same blog)
  4. Reducing the load — run high-volume automated processes serially, in off-peak windows, or with smaller batch sizes to reduce lock duration and contention with end users (source: same blog)

Junction Object Skew

One record on either side of an M:M junction has too many junction records.

Impact: Same lock contention as lookup skew; cascading deletes become extremely slow.

Fix: Limit relationship depth; consider soft-delete pattern instead of cascading.

Not independently verified

No official Salesforce source could be confirmed for this section specifically — checked the DRAES ownership-skew doc, the Managing Lookup Skew blog, and both current LDV developer guides (Introduction, Best Practices) — none name “junction object skew” directly, and web search via available tooling did not surface a usable source as of 2026-09-24. Content here is an inference: a junction object’s two lookup/master-detail fields are subject to the same general lookup-locking mechanism described in Lookup Skew — so this section is likely a specific case of that mechanism rather than a separate one, but that framing itself is unconfirmed.

Exam trap

Ownership skew and lookup/account skew have different root causes and different fixes. Don’t conflate them.

Indexes

(Indexes for SOQL Query Performance · LDV — Standard and Custom Indexes)

Standard Indexes (auto-created) — 30% tier

Platform-maintained indexes on most objects:

  • Primary key: the unique Salesforce record Id; plus Name, OwnerId
  • Foreign keys: lookup & master-detail relationships (also CreatedById, LastModifiedById)
  • Audit / system: CreatedDate, SystemModstamp (LastModifiedDate), RecordTypeId, Division
  • Email (on Contact and Lead)

Divisions

A Setup feature (Company Settings → Divisions) that adds a standard Division picklist field to major objects (Account, Contact, Opportunity, Lead, Case, and enabled custom objects), letting users work within one active division at a time and scope list views, reports, and search to it.

How it helps LDV performance: Division is part of the platform’s standard, auto-created index set (same tier as Id, Name, OwnerId, CreatedDate — see Standard Indexes (auto-created) — 30% tier). Filtering or reporting by division is therefore a selective, indexed lookup rather than a full scan, so on a very large object split across business units by division, division-scoped queries/reports avoid touching the full row count.

Not independently verified

Division’s standard-index status is sourced from the LDV Best Practices developer guide (cited above). The description of what Divisions does and its performance rationale could not be confirmed against a live official article as of 2026-09-24 — Salesforce Help (help.salesforce.com) renders client-side only and returns no fetchable content for any article ID, and the current LDV Best Practices / Introduction developer guides don’t mention Divisions at all (it’s a legacy Setup feature, not part of the current LDV guide). Treat this section as a reasonable inference from the indexed-field fact, not a directly quoted source. Also note: Divisions only scopes queries/UI to an active division — it does not reduce actual data storage or change sharing computation, so it isn’t a substitute for archiving, skinny tables, or sharing-cost reduction.

Custom Indexes — 10% tier (stricter)

  • Auto-created on custom fields marked External ID or Unique. External IDs are allowed only on Auto Number, Email, Number, Text field types
  • Created on request — via Salesforce Customer Support, or by deploying a custom index XML file through the Metadata API. For other/standard field types, go through Support
  • Support-created custom indexes in production are copied to all sandboxes made from that org (contrast with skinny tables, which only Full sandboxes get automatically)
  • These use the stricter 10% threshold — being “auto-created” does not make External ID / Unique fields standard indexes

Fields that can't be custom-indexed

Long text areas, rich text areas, encrypted text, multi-select picklists, and non-deterministic formula fields. Deterministic formulas can be indexed; a formula is non-deterministic if it references other entities / cross-object fields, uses dynamic date-time (TODAY, NOW), or references owner / autonumber / division / audit fields (except CreatedDate & CreatedById), currency fields in a multi-currency org, etc. Some special standard fields are also non-indexable (e.g. Opportunity Amount / ExpectedRevenue / IsClosed / IsWon; Case ClosedDate / IsClosed; Product IsActive / IsArchived).

Index tables & null rows

Because the multitenant custom-field storage isn’t directly indexable, Salesforce builds a separate index table (a copy of the field data + type info) and indexes that. By default the index table excludes null rows — which is why WHERE Field__c = null typically can’t use the index. You can ask Support to create a custom index that includes nulls, but you must explicitly enable and rebuild it.

Selectivity Thresholds

Salesforce’s query optimizer only uses an index when the query is selective — i.e. the filter is expected to return few enough records that an index scan beats a full table scan. The threshold is tiered and cumulative (percentages apply to record bands), with exactly two tiers: standard and custom. (LDV — Standard and Custom Indexes)

Index tierFieldsSelective when matched rows are belowHard cap
StandardId, Name, OwnerId, lookup/master-detail FKs, CreatedDate, SystemModstamp, RecordType, Division30% of first 1M + 15% of rows beyond 1M1,000,000
CustomExternal ID, Unique, Support-created custom indexes10% of first 1M + 5% of rows beyond 1M333,333

Worked example (custom index, 2M-row object): threshold = (10% × 1,000,000) + (5% × 1,000,000) = 150,000. Match < 150k ⇒ index; ≥ 150k ⇒ table scan. Exceeding the first-million tier alone disqualifies the index, regardless of the rows-beyond-1M band.

Two tiers only — common myths

There are only two threshold tiers: standard = 30% / 15%, custom = 10% / 5%. Beware incorrect claims that “the primary-key/Id index has a 10% threshold” (it’s a standard index → 30%) or that “custom indexes are 15%” (15% is the standard index’s rate for rows beyond the first million). External ID / Unique fields are custom indexes (10%), even though auto-created.

AND (composite) queries — double-threshold rule

For filters combined with AND, the optimizer treats the overall condition as selective if either: (a) each individual filter targets < 2× its own threshold — the “2×” is fixed and does not scale with the number of conditions — or (b) the intersection of all the AND’d filters targets < 1× the threshold. Salesforce calls this a Composite Index Join.

LDV guide phrasing — AND / OR / LIKE

The LDV Best Practices guide summarises the multi-filter rules as:

  • AND — indexes are used unless one filter returns > 20% of the object’s records.
  • OR — indexes are used unless all filters return > 10%, and every field in the OR must be indexed for any index to be used.
  • LIKE — the optimizer ignores its statistics table and instead samples up to 100,000 actual records to decide whether to use the custom index.

If one indexed field’s criteria aren’t met, only that index is dropped — other qualifying indexes in the WHERE clause may still be used.

When indexes are NOT used

  • CONTAINS operator: requires full index scan; only used if rows to scan < 333,333
  • Negative operators: !=, NOT IN, NOT CONTAINS, NOT STARTS WITH
  • Empty value comparisons: Name != ''
  • Filter returns > threshold records regardless of index

CTA application

When designing for LDV, always identify which fields appear in WHERE clauses and verify they are index-eligible and selective. A custom index on a low-cardinality field (e.g. Status with 3 values) will rarely be selective enough to be used. The commonly cited rule of thumb is < 200k records on objects with > 2M records total.

Additional Index-Bypass Cases

(LDV — Standard and Custom Indexes — unverified against current page text as of 2026-09-23; recheck before quoting)

  • LIKE '%value' (leading wildcard)
  • Functions on indexed fields: WHERE UPPER(Name) = ...
  • Null comparisons: WHERE Field__c = null (use = '' for text or handle in code)
  • OR conditions spanning multiple non-indexed fields

Design principle

Always design your data model so that the fields used in WHERE and ORDER BY clauses are index-eligible. Flag this explicitly in the CTA presentation.

Skinny Tables

(Skinny Tables Help article — sf.performance_skinny_table.htm — no longer appears in Salesforce’s current Help sitemap; no live replacement found as of 2026-09-23 · LDV Skinny Tables · LDV Best Practices PDF)

Skinny tables speed up read-only operations (reports, list views, SOQL) on tables with millions of records by avoiding joins between standard/custom field storage and omitting soft-deleted rows.

  • Soft-deleted rows are excluded, so scans touch only live data.

  • Must be requested via Salesforce Support (not self-service)

  • Creates a narrow copy with only needed columns for a query pattern

  • Kept in sync when source data changes

  • Max columns: up to 200 (current LDV guidance)

  • Can’t contain fields from other objects — single base object only (no cross-object/related fields)

  • Skinny tables (and skinny indexes) can also contain encrypted data

  • Full sandboxes: skinny tables are copied automatically

  • Other sandbox types: skinny tables are not copied — contact Salesforce Customer Support to activate production skinny tables for non-Full sandboxes

Supported objects: Account, Contact, Opportunity, Lead, Case, and custom objects.

Supported field types: Checkbox, Date, Date/Time, Email, Number, Percent, Phone, Picklist (multi-select), Text, Text Area, Text Area (Long), URL.

Pre-computed field pattern (avoid repeated computation)

Instead of filtering on an expensive date range like CloseDate >= 01/01/11 AND CloseDate <= 12/31/11 — a repeated computation for annual or year-to-date reports — add a Year field to the skinny table and filter on Year = '2011'. Materializing the derived value into a stored, skinny-table-backed field turns a range scan into a cheap equality lookup.

Sharing & LDV

Sharing recalculation is the most expensive operation at scale. (Sharing Recalculation and LDV)

Per-object sharing rule caps (and Support increase maxes): Sharing rule limits.

Strategies to Reduce Sharing Cost

StrategyWhen to use
Fewer sharing rulesSimplify role hierarchy; avoid complex criteria-based sharing
Defer sharing recalculationDuring bulk data loads — re-enable after load completes
Parallel sharing recalculationAvailable for Accounts; request via Salesforce Support
Private OWD + Apex managed sharingFull control; avoid rule proliferation
Territory ManagementFor Account-heavy orgs needing complex geo/product-based access

Warning

Criteria-based sharing rules with LDV are dangerous — each rule evaluation touches every record during recalculation. Prefer owner-based sharing rules or Apex sharing for LDV objects. (Sharing Model Fields)

Archiving & Data Retention

When records can’t be kept in the active working set, move them out on a governed schedule (aligned with data stewards on the governance board) rather than letting volume grow unbounded.

  • Default CTA answer: off-platform archive (data lake / warehouse) with on-demand access via OData / Salesforce Connect or an LWC — keep the active working set in Salesforce.
  • Big Objects (__b) are native but read-only, index-fixed, and no sharing — use only when the access pattern is defensible.
  • External objects give a live view without storage cost, at the price of latency and no sharing model.
  • Archive during migration where possible instead of loading old data in and archiving later.

Full detail

Options table, access patterns, Big Objects facts, the Data Warehouse pattern, and backup/restore are in data-archiving-and-backup.

Batch Processing & LDV

(Batch Apex Developer Guide)

  • Use Database.QueryLocator (up to 50M records) vs Iterable (50k limit) for large datasets
  • Set batch size conservatively (200 default; lower if each record triggers complex logic)
  • Avoid SOQL inside loops — all queries must be bulkified
  • Chain batches for multi-step processing; use AsyncApexJob to monitor
  • Platform Events + triggered flows/batches preferred for near-real-time at scale (Platform Events Developer Guide)

Tip

For migrations, use Bulk API 2.0 (parallel jobs). Avoid REST/SOAP for LDV loads. (Bulk API 2.0 Developer Guide) See also bulk-api-and-cursors.

Reporting on LDV

  • Reports timeout at 10 minutes
  • Dashboards refresh async — less of a concern but data can be stale
  • Mitigations:
    • Add indexed filters to all LDV reports (Indexes for SOQL Query Performance)
    • Use report filters on RecordType, OwnerId, CreatedDate (all indexed)
    • Consider CRM Analytics (Tableau CRM) for large-scale reporting — extracts data out of the transactional store
    • Async SOQL / Data Pipelines for scheduled aggregation into summary objects

Design Checklist for LDV Scenarios

  • Identify which objects will exceed 1M records (flag 50M+ for mandatory archive/offload)
  • If Account/Contact + Experience Cloud users → avoid casual archive; plan monitoring + indexes/skinny tables
  • Confirm OWD and sharing model — flag recalculation risk
  • Check for ownership skew (integration users, queues; ~10k+ owned by one user)
  • Check for lookup/account skew (~10k+ children on one parent)
  • Identify query patterns → ensure indexed fields in WHERE/ORDER BY
  • Define archiving strategy (Big Objects, warehouse/EDW, external, off-platform) with governance owners
  • Plan bulk load approach (Bulk API 2.0, parallel jobs)
  • Address reporting needs (indexed filters, CRM Analytics)
  • Consider skinny tables for critical read-only query paths (Support-managed)
