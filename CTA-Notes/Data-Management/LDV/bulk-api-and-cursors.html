Sample Build Scenario — “Meridian Retail”

Used throughout this note to make each feature concrete. Meridian Retail is migrating off a legacy on-prem ERP into Salesforce and has six distinct data-movement needs, each mapped to a different feature below:

#NeedVolumeFeature used
1One-time historical load of closed Orders8M recordsBulk API 2.0 ingest
2Nightly incremental extract of Accounts/Contacts to a BI warehouse~3M records/nightBulk API 2.0 query
3Legacy invoicing middleware writing ledger-ordered Invoice records500k records, strict orderBulk API 1.0 ingest (serial mode)
4One-off compliance audit extraction of historical Cases12M recordsBulk API 1.0 query + PK chunking
5”My Open Orders” panel in a Lightning component< 2,000 records/callREST API query + nextRecordsUrl cursor
6Nightly Apex job recalculating loyalty tier from lifetime spend4M ContactsApex Database.Cursor

Bulk API 1.0 vs 2.0 Comparison

(Bulk API 2.0 and Bulk API Developer Guide — Introduction)

FeatureBulk API 1.0Bulk API 2.0

Batch managementManual — you create and monitor batchesAutomatic — platform manages batching

Default choice

Use Bulk API 2.0 for all new work. 1.0 is only needed when you require serial concurrency mode or are integrating with a legacy system that already uses it.

Hard delete

hardDelete requires the “Bulk API Hard Delete” permission. Use with caution — records are not recoverable from the recycle bin.

Build it: Meridian Retail — need #3 (ledger-ordered Invoices)

Meridian’s legacy invoicing middleware must write Invoice__c records in strict chronological order because downstream ledger reconciliation depends on insert order. This is exactly the case the comparison table calls out: Bulk API 1.0, Serial concurrency mode. In the job request:

Serial mode processes batches one at a time in submission order — slower, but guarantees no two Invoice__c batches are ever committed out of order. Bulk API 2.0 doesn’t offer this mode, which is why the legacy system is deliberately kept on 1.0 rather than migrated.

Bulk API 2.0 — Job Lifecycle

(Bulk API 2.0 Ingest · Get Job Information · Upload Job Data)

Create Job → Upload CSV batches → Close Job → Poll for completion → Retrieve results
  1. POST /jobs/ingest — create job, specify object and operation
  2. PUT /jobs/ingest/{jobId}/batches — upload CSV (repeat for large files)
  3. PATCH /jobs/ingest/{jobId} with state: UploadComplete
  4. GET /jobs/ingest/{jobId} — poll until state: JobComplete
  5. GET /jobs/ingest/{jobId}/successfulResults and failedResults

Build it: Meridian Retail — need #1 (8M historical Orders)

The one-time historical Order migration is the textbook Bulk API 2.0 ingest case: a single, huge, one-shot load with no ordering requirement.

1. POST /services/data/v62.0/jobs/ingest
   { "object": "Order", "operation": "insert", "lineEnding": "LF" }
   → returns jobId + contentUrl

2. PUT {contentUrl}   (repeat per CSV chunk, e.g. 10 files of ~800k rows each)
   Content-Type: text/csv
   OrderNumber,AccountId,EffectiveDate,Status
   LEG-000123,001xx0000...,2019-03-01,Activated
   ...

3. PATCH /services/data/v62.0/jobs/ingest/{jobId}
   { "state": "UploadComplete" }

4. GET /services/data/v62.0/jobs/ingest/{jobId}   (poll every 30-60s until JobComplete)

5. GET /services/data/v62.0/jobs/ingest/{jobId}/failedResults
   → feed rejected rows into a remediation CSV for a second pass

At 8M records against the 150M-records/24h org cap, this single job consumes a modest slice of the daily allocation — worth flagging in a design review if Meridian also runs nightly loads (need #2) on the same day.

Note

For reporting/extraction at scale, prefer Bulk API 2.0 Query + cursor pagination over REST API queryMore. The REST API query cursor has a short inactivity expiry and is not suited for very large result sets.

Build it: Meridian Retail — need #2 (nightly 3M-record BI extract)

A scheduled job (outside Salesforce — e.g. an integration platform) runs nightly:

1. POST /services/data/v62.0/jobs/query
   { "operation": "query", "query": "SELECT Id, Name, LastModifiedDate FROM Account WHERE LastModifiedDate = TODAY" }

2. GET /services/data/v62.0/jobs/query/{jobId}   (poll until JobComplete)

3. GET /services/data/v62.0/jobs/query/{jobId}/results
   → CSV stream, paginated via the `Sforce-Locator` response header

Using LastModifiedDate = TODAY (delta only, not a full extract) keeps each night’s job well under the 3M full-table size and avoids re-shipping unchanged rows to the warehouse.

Salesforce Cursors

There are three distinct “cursor” concepts in Salesforce — easy to conflate.

1. REST API Query Cursor

(Query Resource)

  • Created implicitly when a SOQL query result exceeds the batch size (default, and max, 2,000 records per synchronous response — confirmed on the current Query resource page)
  • Returns nextRecordsUrl in the response; call it repeatedly to page through results
  • This note previously stated a hard “10-minute inactivity expiry” and a “max 10 cursors per user session” — neither figure could be re-confirmed on the current Query resource page as of 2026-09-30. Treat both as unverified rather than exam-quotable facts until a live source is found.
  • Not suitable for LDV extraction — use Bulk API 2.0 instead

2. Apex Database Cursor (Summer ‘24+)

(Database.Cursor class reference)

A native Apex API for scrollable, stateful SOQL iteration — designed specifically for LDV processing without chaining Batch Apex jobs.

Key facts (re-verified 2026-09-30):

  • Created with Database.getCursor(query) or Database.getCursorWithBinds(query, bindMap, accessLevel)
  • Scrollable: fetch(position, count) — up to 2,000 records per call
  • Max 50 million rows per cursor, sync or async
  • Max 100 Cursor.fetch() calls per transaction
  • Calling fetch() counts against the SOQL query limit, and rows fetched count against the SOQL row limit — this is a real governor-limit cost, not a free ride
  • This note previously stated “cursor valid for 24 hours,” “max 5 open cursors per org,” and “does not consume Batch Apex concurrency slots.” None of these three could be re-confirmed on the current class reference page as of 2026-09-30 — the page instead confirms fetch() calls DO count against ordinary SOQL limits. Treat the three unconfirmed figures as legacy/unverified, not settled facts.

Typical use pattern:

When to use Database Cursor vs Batch Apex

Use Database Cursor when you need stateful, scrollable iteration in a single Apex context (e.g. a Queueable chain) and don’t need parallel processing. Use Batch Apex when you need parallel execution or the volume exceeds what a single cursor lifecycle can handle.

Warning

Database Cursor is a relatively new feature (Summer ‘24). Confirm API version support in the target org before recommending it in a CTA scenario, and remember fetch() calls consume ordinary SOQL governor limits — a naive loop can still hit LimitException.

Build it: Meridian Retail — need #6 (nightly loyalty-tier recalc, 4M Contacts)

At 4M Contacts ÷ 2,000/fetch = 2,000 fetch calls total — well over the 100 fetch() calls per transaction limit, so this must be chained across multiple Queueable transactions (as shown, re-enqueuing every batch) rather than looped in one execution. This is exactly the kind of governor-limit interaction the newly-confirmed 100-calls-per-transaction limit changes about how you’d design this job.

3. Bulk API Cursor (PK Chunking)

(Enable PK Chunking)

  • Splits a large query into sub-queries by primary key range (chunks)
  • Enabled via Sforce-Enable-PKChunking: true header
  • Default chunk size: 100,000; max: 250,000 (confirmed on the current guide page)
  • Each chunk is processed as a separate batch that counts toward the daily batch limit
  • Whether Bulk API 2.0 query jobs still need this header manually, or chunk automatically, could not be confirmed — see the caution in the comparison table above

Build it: Meridian Retail — need #4 (12M-record compliance audit of historical Cases)

The audit tool is a legacy Bulk API 1.0 client, so PK chunking must be opted in manually:

POST /services/async/62.0/job
Header: Sforce-Enable-PKChunking: chunkSize=200000

<jobInfo>
  <operation>query</operation>
  <object>Case</object>
  <contentType>CSV</contentType>
</jobInfo>

12M records ÷ 200,000/chunk = 60 chunks → 60 auto-created batches, each independently retryable if one chunk times out — far more resilient than one 12M-row batch, and it avoids the query-level timeout that a single unchunked query against 12M Cases would likely hit.
