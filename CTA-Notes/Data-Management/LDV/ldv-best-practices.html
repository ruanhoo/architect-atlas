Two Guiding Principles

Almost every LDV best practice reduces to one of two levers (Best Practices):

  1. Make it selective — write narrow queries/reports/list views that reference indexed fields so the optimizer scans fewer rows. A report by one city in one state beats a report by all cities in a state.
  2. Reduce active data — archive or discard at the same rate data arrives, so the working set stays small (see Archiving & Data Retention).

CTA framing

If asked “how do we keep this performant at scale?”, anchor your answer on these two levers, then cite the specific technique (selective filters + indexing, skinny tables, defer sharing, Bulk API, archiving to Big Objects).

Reporting

GoalBest practice
Maximize report performanceSegment on a data value (e.g. one state, not all states); partition data to match usage; minimize records per object
Reduce joinsMinimize objects and relationships in the report; de-normalize by rolling summary values onto the parent record rather than summarizing children at run time (don’t over-de-normalize)
Reduce data returnedQuery only required fields in reports, list views, and SOQL
Reduce records to queryArchive unused records to a custom object; filter on indexed fields wherever possible

Loading Data from the API

GoalBest practice
Improve throughput> 2,000 records → Bulk API 2.0 (async). Fewer than 2,000 → bulkified synchronous REST (Composite) or SOAP
Most efficient opinsert() > update() > upsert(). If possible split upsert into create + update. Clean data first — batch errors trigger slow single-row processing
Reduce data movedSend only changed fields (delta-only updates)
Reduce transmission costAuthenticate once per load (not per record); use GZIP + HTTP keep-alive
Avoid sharing computationUse Public Read/Write during the initial load to skip sharing calc
Order sharing setupLoad users into roles → record data (owners) → groups/queues → sharing rules one at a time, letting each finish
Defer computationDisable triggers, workflow/flows, and validation rules during load; reprocess with batch Apex afterward

Ownership skew during load

Combine with ownership-skew avoidance: don’t let one user own > 10,000 records, or sharing recalculation on load becomes a bottleneck.

Extracting Data from the API

GoalBest practice
Batch size vs timeoutsSOAP: use as many batches as possible (up to 200) that still avoid network timeouts when records are large or processing is heavy
Java clientsUse the WSC (Web Service Connector) rather than Axis
Avoid lock conflictsGroup child records by ParentId in the same batch
Defer sharingUse the Defer Sharing Calculation permission until after all data is loaded
Avoid loading at allUse mashups for coupled integrations (leave data in the source system)
Efficient syncgetUpdated() / getDeleted() for syncs at intervals > 5 min; outbound messaging for more frequent syncs; Bulk API 2.0 Query for results > 1M rows

Searching

GoalBest practice
Fewer records returnedKeep searches specific; avoid wildcards (Michael, not Mi*)
Fewer joinsPrefer single-object searches for speed and accuracy
EfficiencyEnable language optimizations; turn on enhanced lookups and auto-complete for lookup fields

SOQL & SOSL

SOQL

  • Use selective filters on indexed fields with a wide value range — non-selective filters bypass the index.
  • Filter on Name instead of FirstName + LastName.
  • Avoid negative filters (status != 'failed', field != NULL).
  • Use IN instead of a long chain of ORs.
  • Avoid cross-object reference formula fields — they aren’t indexable.
  • If two indexed fields are joined by OR and the result can exceed the index threshold, decompose into two queries and merge results in code.
  • Avoid querying/filtering on non-deterministic formula fields (see Custom Indexes — 10% tier (stricter)).
  • Replace nulls with a sentinel like NA for picklist/foreign-key filters (nulls can’t use the index).

SOSL

  • Selective filters cut irrelevant results; > 2,000 matches risks search crowding.
  • Don’t index custom objects you don’t want searched; filter out unwanted objects.
  • Use specific terms and targeted search groups (NAME, EMAIL, PHONE), e.g. FIND 'Avery Smith' IN NAME FIELDS RETURNING Account(Id,Name), Lead(Id,Name).

Avoiding SOQL timeouts

Tune scope + selective filters first. Then consider Bulk API 2.0 Query, or add a LIMIT (start at 100,000). In batch Apex, use chaining with LIMIT or push filter logic into the execute method.

Deleting Data

GoalBest practice
Delete ≥ 1M recordsUse Bulk API hard delete (skips the Recycle Bin)
Records with many childrenDelete children first
Keep queries fastEmpty the Recycle Bin — soft-deleted rows still affect query performance

General & Sandboxes

GoalBest practice
Avoid sharing computationNo user should own > 10,000 records
Improve performanceData-tiering — spread data across objects, bring in on demand from another object or external store
Faster full sandbox copiesExclude field history if not needed; don’t mass-change data until the copy completes
Efficient deploymentsDistribute child records so no parent has > 10,000 children (e.g. dummy accounts to spread orphan contacts)

Case Studies

Real customer problems from the guide, written as Situation → Solution → Takeaway so they double as ready-made board answers. (Case Studies)

Sort Optimization on a Query — ORDER BY + LIMIT to force index use

  • Situation: A “records from the last 3 days” query performed poorly because the object had grown past the standard-index threshold (30% of the first 1M rows), so the optimizer skipped the CreatedDate index and table-scanned.
  • Solution: Add ORDER BY on the indexed field plus a LIMIT under 100,000. Threshold checks are skipped and the CreatedDate index drives the query.

Exam-gold pattern — ORDER BY index trick

When querying data added over the LAST_N_DAYS and the filter alone isn’t selective enough, an ORDER BY on an indexed field with LIMIT < 100,000 lets the optimizer use that index and bypass threshold evaluation. Returns up to 99,999 rows in created order. (Sort Optimization case study)

Indexing with Nulls — sentinel value or formula index

  • Situation: The customer needed to allow nulls in a field and query for them. Single-column indexes for picklists and foreign keys exclude null rows, so no index could serve WHERE Status__c = ''.
  • Solution (preferred): Don’t store nulls — use a sentinel like N/A so the value is indexable.
  • Solution (if nulls already exist): Index a formula field that maps blanks to text, then filter on the formula.
  • Takeaway: Extends to multiple fields (WHERE Status_Value__c = '' OR Email = ''). See Index tables & null rows.

Data Aggregation — pre-compute with batch Apex

  • Situation: Monthly (4M) and yearly (9M) metrics stored in custom objects; standard reports aggregated across millions of rows and were slow.
  • Solution: Create an aggregation custom object that stores the summarized values in report-ready form, populated by batch Apex; run reports off the summary object.
  • Takeaway: Trade real-time aggregation for pre-computed roll-ups when the source volume is large.

Custom Search Functionality — restrict fields, de-normalize, pick SOQL vs SOSL

  • Situation: A Visualforce search let users enter 1–20 arbitrary fields with wildcards across multiple objects — impossible to tune, and wildcards/multi-object joins were slow.
  • Solution: Limit to essential search fields (so Salesforce can tune indexes); de-normalize the multiple objects into one custom object to avoid multi-query calls; dynamically choose SOQL or SOSL — specific (no-wildcard) values → SOQL to leverage indexes.

Rendering Related Lists — data skew + separate loading

  • Situation: Hundreds of thousands of accounts with 15M invoices (master-detail); some parents had thousands of children, so account pages rendered slowly.
  • Solution: Root cause was lookup/parent data skew — reduce children per parent and keep skew minimal; enable Separate Loading of Related Lists so account detail renders while the related-list query completes.
  • Takeaway: Cross-link lookup skew.

API Performance — don’t filter with sharing

  • Situation: A custom integration used a sharing-scoped API user to limit records; queries over several-million-row objects took minutes.
  • Solution: Give the query access to all data (e.g. an admin API user) and use selective filters instead of sharing as the filter; add a delta extraction to reduce volume.
  • Takeaway: Sharing is great for UI visibility, poor as a high-volume query filter.

Multi-Join Report Performance — filter, trim, clean

  • Situation: A report joined 4 related objects (Accounts 314k, Sales Orders 769k, Sales Details 2.3M, Account Ownership 1.2M) with very little filtering.
  • Solution: Add selective, indexable filters; reduce data per object; empty the Recycle Bin (soft-deleted rows slow queries); remove complex sharing rules on the joined objects.
