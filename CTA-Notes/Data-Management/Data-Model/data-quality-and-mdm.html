Data Quality & Master Data Management

Data Quality & Master Data Management

Nov 14, 20266 min read

  • mdm

Covers keeping Salesforce data clean, unique, and trustworthy — both at migration time and in steady state — and deciding which system owns which data when several systems hold the same entity (customer, product, etc.).

Exam framing

Most multi-system scenarios imply a master-data question even if the word “MDM” never appears. State the system of record per entity, how duplicates are prevented/resolved, and who owns data quality (governance).

Dimensions of Data Quality

DimensionQuestionTypical Salesforce control
CompletenessAre required values present?Required fields, validation rules, page-layout/record-type rules
ValidityDoes the value conform to format/domain?Restricted picklists / global value sets, validation rules, field types
UniquenessIs the entity stored once?Duplicate/matching rules, unique External ID fields
ConsistencyDo systems agree?System-of-record decision, integration, MDM
Accuracy / TimelinessIs it correct and current?Enrichment, review cadences, integration sync

Prevention vs Detection vs Cure

StageApproachExamples
Prevent (best)Stop bad data enteringValidation rules, restricted picklists, duplicate rules set to Block, address/email validation at entry, integration contracts
DetectFind problems that got inReports/dashboards on completeness, duplicate jobs, data-quality scorecards
CureFix existing dataMerge duplicates, mass update, enrichment batch runs, cleansing in the ETL (data-migration)

Rule of thumb

Cleaning data once is cheap; keeping it clean needs prevention and an owner. Pair every cleansing exercise with a prevention control and a governance role.

Duplicate Management in Salesforce

Native Duplicate Management uses two building blocks:

ComponentRole
Matching ruleDefines how two records are considered a match (fields, exact/fuzzy logic). Standard rules are provided for Account, Contact, Lead; custom rules can be created.
Duplicate ruleDefines what happens when a match is found: Block or Allow with alert, and whether to Report the match. Can run on create and/or edit.
  • Supports Accounts, Contacts, Leads, Person Accounts, and custom objects; rules can match across objects (e.g. a new Lead against existing Contacts).
  • Detected duplicates are stored as Duplicate Record Sets / Items and can be surfaced in reports.
  • Records are merged via the standard merge flow (up to three records at a time for Accounts, Contacts, Leads).
  • Duplicate rules can be bypassed for API loads by the caller (useful in migration — then run a separate detection pass afterwards).

Limits of native duplicate management

It is a detect-and-resolve-in-Salesforce tool. It does not make Salesforce the master for a customer that is mastered elsewhere, and it does not reconcile conflicting attribute values across systems (survivorship). For that you need an MDM approach (below).

Verify before quoting limits

Per-object rule counts, batch duplicate-job availability by edition, and cross-object matching scope vary by release/edition — confirm in Salesforce Help (“Duplicate Management”) before citing numbers in a board answer.

Enrichment & Validation

Third-party AppExchange / external services typically cover:

  • Address / email / phone validation at entry or in batch
  • Firmographic enrichment (company size, industry, hierarchies) from commercial data providers
  • Fuzzy dedup and merge beyond native matching (specialised dedup tools)

The CTA study guide lists Data Enrichment & Validation among the AppExchange categories to know at a high level: how it works, when to use it, and how it integrates (callout/real-time at entry vs. scheduled batch). See cta-study-guide-overview.

The legacy native Data.com / Data.com Clean offering is retired — don’t propose it as a solution. Name a current provider category rather than a retired product.

Master Data Management

MDM = a governed way to produce a single trusted view (the golden record) of key entities across systems.

Key terms

  • System of record (SoR): the authoritative system for an entity or attribute.
  • Golden record: the consolidated, best-version record.
  • Survivorship rules: which source wins per attribute when values conflict (most recent, most trusted source, most complete).
  • Match & merge: identifying that records across systems are the same entity.
  • Cross-reference (xref) key: mapping of each system’s ID to the master ID — often implemented with Salesforce External IDs.

MDM implementation styles

StyleHow it worksProsConsWhen to use
RegistryHub holds only match keys / cross-references; data stays in sources, read through on demandMinimal intrusion; quick to stand upCross-system reads can be slow; no cleansed golden copy written backMany sources, low appetite to change them; read-mostly use
ConsolidationHub copies data from sources, cleanses and matches it, and serves a golden record (read-only to sources)Good analytics/reporting view; sources unchangedGolden record is not pushed back; latency vs. sourcesReporting/BI-driven mastering
CoexistenceGolden record is created in the hub and synchronised back to sources, which still allow editsConsistent across systems; sources remain usableComplex bidirectional sync and conflict handlingSeveral systems must stay live and aligned
Centralised (transaction)Hub is the sole place records are created/edited; sources consumeStrongest consistencyLarge change to existing systems and processesGreenfield or when sources can be re-pointed

Where Salesforce fits

RoleNotes
Salesforce as customer SoRCommon for Sales/Service-led companies: Account/Contact is mastered in Salesforce and published to ERP/billing via integration (Integration Patterns)
Salesforce as consumer of a hubAn external MDM (or ERP) is the SoR; Salesforce receives the golden record and holds an External ID xref
Data Cloud identity resolutionUnifies profiles across sources using match and reconciliation rules for activation/analytics — a unified profile, not a replacement for transactional MDM
MuleSoft / iPaaSOrchestration layer that routes and transforms between SoR and consumers; not an MDM by itself (50-mulesoft)

Say it explicitly in a scenario

For each shared entity: “X is mastered in system A; Salesforce holds a read/replicated copy keyed on External ID; conflicts resolved by rule R; sync via pattern P.”

Data Governance

Data quality fails without owners. Typical roles to name on the governance board:

RoleResponsibility
Data ownerAccountable executive for an entity/domain; sets policy
Data steward / custodianDay-to-day quality, dedup decisions, retention schedule
Data architectModel, standards, integration contracts
Admin / DevOpsImplements controls (validation, rules, jobs)

Governance outputs worth mentioning: data dictionary, quality KPIs (duplicate rate, completeness %), review cadence, retention and archiving policy (data-archiving-and-backup), and privacy handling (privacy-and-consent-management).

Design Checklist

  • System of record identified per shared entity
  • MDM style chosen (or explicitly “not needed” with reason)
  • Duplicate prevention at entry + detection job + merge process
  • Cleansing done before load; prevention controls active after
  • External IDs / xref keys for cross-system matching
  • Enrichment/validation approach (real-time vs batch) named
  • Governance owners and KPIs defined
