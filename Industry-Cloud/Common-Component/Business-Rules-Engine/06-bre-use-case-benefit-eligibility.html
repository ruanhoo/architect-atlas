BRE Use Case: Benefit Eligibility

BRE Use Case: Benefit Eligibility

Nov 27, 202613 min read

  • industry-cloud
  • business-rules-engine
  • public-sector

End-to-end walkthrough demonstrating decision matrix vs decision table, matrix types (standard vs grouped), expression set orchestration, versioning, and explainability. Includes setup steps with screenshot placeholders. Customer is fictional. Background: 01-business-rules-engine-overview, 02-expression-sets, 03-decision-matrices-and-decision-tables, 04-decision-explainer, 05-bre-integration-and-operations.

Context

Harbor County Housing administers a rent-assistance program:

  • ~120k applications/year; spike to ~40k in the first two weeks of the annual enrollment window
  • Caseworkers use Salesforce (Public Sector Solution); applicants use an Experience Cloud portal with Omnistudio intake
  • Policy changes yearly (income thresholds, subsidy rates) and occasionally mid-year by emergency order
  • Policy analysts (not developers) maintain the numbers
  • Applicants and auditors must see why a determination was made
  • Each county service office has caseload rules stored as records (office, postcode, program), maintained by operations via normal UI and data loads

Requirements

Functional

  1. Compute household eligibility from household size, gross income, and region
  2. Compute monthly subsidy: base rate (by size + region) + add-ons (dependents, disability, emergency uplift)
  3. Route each approved application to the correct service office and caseworker group
  4. Run the same rules in the portal (real time), caseworker Flow, and nightly over the whole open caseload
  5. Show readable explanations to applicants and auditors

Non-functional

  • Policy changes schedulable by effective date without deployment
  • Rules maintained by analysts; no Apex for rule logic
  • Portal determination in a single interactive call; nightly recalculation of up to ~120k applications
  • Guest/community users can run determinations but not edit rules

Why Decision Matrix vs Decision Table?

AspectDecision MatrixDecision Table
Data sourceRows/columns in the matrix itselfRecords in a standard/custom object or custom metadata type
Who owns itPolicy analysts edit CSV filesOperations maintains records via normal UI or data loads
VersioningBuilt-in: start/end date + rank; multiple versions active, highest rank winsActivate/refresh; no built-in effective dating
When source changesUpload new CSV or create new versionMust refresh the table (async operation)
Duplicate data?Yes — matrix holds a copy of the numbersNo — table reads records in place
Best forSmall-to-medium grids of policy numbers that change on a scheduleRules already stored as records; larger datasets
Limits100 MB CSV; 200 input sets per lookup100k rows; 10 outputs; needs CreatedDate + IsDeleted on source object

This use case:

  • Subsidy rates → decision matrix (analysts own, CSV edits, fiscal-year versions)
  • Service office routing → decision table (operations already maintains area records)

Decision Matrix Setup: Subsidy Rates (Grouped Matrix)

Why Grouped?

A grouped decision matrix avoids repeating the region column in every row. The matrix key (region) becomes an input variable; only the matching version is considered for lookup.

Without grouping (standard matrix):

1             | North   | 25000         | 400
2             | North   | 35000         | 650
3             | North   | 45000         | 850
1             | South   | 22000         | 380
2             | South   | 32000         | 620
...

With grouping (grouped matrix, key = Region):

  • Version “North”: only North rows
  • Version “South”: only South rows

Setup Steps

  1. App Launcher → Business Rules Engine → Lookup Tables → New
  2. Select Decision Matrix → Next
  3. Enter:
    • Name: Subsidy_Rates_FY2027
    • Type: Grouped
    • Matrix Key: Region (Text)
  4. Save
  5. On the Related tab, click the first version
  6. Add Column:
    • Input columns: HouseholdSize (Number), IncomeCeiling (Currency)
    • Output columns: BaseSubsidy (Currency)
  7. Add Rows (manual or CSV upload):
    • For key value “North”: 3 rows (household sizes 1–3)
    • For key value “South”: 3 rows
  8. Set version start date, rank, and Activate

Adding a Second Fiscal Year

  1. Create new version in the same matrix: Subsidy_Rates_FY2028 V1
  2. Set start date = 2027-07-01, rank = 2 (higher than FY2027’s rank 1)
  3. Upload new CSV or manually edit rows
  4. Activate

Both versions are now active; when the expression set passes effectiveDate = 2027-08-01, rank 2 wins.

Emergency Uplift (Temporary Override)

  1. Create another version: Subsidy_Rates_FY2027_Emergency V1
  2. Increase BaseSubsidy by 10% in all rows
  3. Set:
    • Start date: 2027-01-15
    • End date: 2027-03-31
    • Rank: 3 (highest)
  4. Activate

From Jan 15 to Mar 31, rank 3 wins; after Mar 31, the original FY2027 version applies again.

Decision Table Setup: Service Office Routing

Why Decision Table?

Operations already maintains Service_Area__c records (office, postcode, program). A decision table reads them in place — no duplicate data to sync.

Object Preparation

Create custom object Service_Area__c (or use an existing one):

  • Must have CreatedDate and IsDeleted fields (standard on custom objects)
  • Fields:
    • Postcode__c (Text)
    • Program__c (Picklist: Rent Assistance, Emergency Housing, …)
    • Service_Office__c (Text or Lookup to Account)
    • Caseworker_Group__c (Text or Lookup to Queue)

Load sample records:

Postcode | Program           | Service_Office | Caseworker_Group
94102    | Rent Assistance   | SF Downtown    | Queue_SF_RA
94102    | Emergency Housing | SF Downtown    | Queue_SF_Emerg
94110    | Rent Assistance   | SF Mission     | Queue_SF_RA
...

Setup Steps

  1. App Launcher → Business Rules Engine → Lookup Tables → New
  2. Select Decision Table → Next
  3. Enter:
    • Name: Service_Office_Routing
    • Type: Standard Decision Table (not Advanced)
    • Source Object: Service_Area__c
  4. Save
  5. Click the table to configure:
    • Input Fields: Postcode__c (Equals), Program__c (Equals)
    • Output Fields: Service_Office__c, Caseworker_Group__c
    • Effective Logic: 1 AND 2 (both inputs must match)
  6. Activate (async; watch DecisionTableActionEvent or poll the status)

Screenshot placeholder

  • Decision table definition: source object, input/output fields
  • Activate button and status
  • Sample source records in the Service_Area__c object

When Source Records Change

Operations adds a new postcode → must Refresh the table:

  1. Open the decision table
  2. Click Refresh (async operation)
  3. Or automate via Flow: on Service_Area__c after-insert/update trigger, call Decision Table Refresh action

Warning

Changes made during activation or refresh may not be picked up. Run Refresh after all updates finish.

Standard vs Advanced Decision Table

FeatureStandardAdvanced
GroupingGroup by up to 2 input fields (Equals)Same
Result filtersFilter outputs after matchingSame
Source filtersPre-filter source recordsSame

Best forMost lookupsVery complex multi-condition rules

This use case uses Standard (simpler setup, sufficient for postcode + program lookup).

Expression Set Orchestration

The expression set ties the matrix and table together, adds calculations, and applies business logic.

Design

  1. Inputs (variables):
    • HouseholdSize (Number)
    • GrossIncome (Currency)
    • Region (Text)
    • EffectiveDate (Date)
    • Postcode (Text)
    • Program (Text)
    • HouseholdMembers (List, via Context Definition if reading from records)
  2. Step 1: Lookup Table → Subsidy_Rates_FY2027 decision matrix
    • Inputs: HouseholdSize, Region, EffectiveDate
    • Outputs: IncomeCeiling, BaseSubsidy (become local resources)
  3. Step 2: Conditional Group
    • Condition: IF GrossIncome > IncomeCeiling
    • True path: set Eligibility = false, TotalSubsidy = 0, stop
  4. Step 3: Branch (priority order for add-ons)
    • Path 1 (highest priority): Emergency order active → set EmergencyUplift = 50
    • Path 2: Disability in household → set DisabilityAddon = 100
    • Default path: no extra uplift
  5. Step 4: List Group + List Filter
    • Filter HouseholdMembers where Age < 18
    • Count → DependentCount
  6. Step 5: Aggregate (if looping over multiple members)
    • SUM of per-dependent add-on: DependentAddon = DependentCount * 25
  7. Step 6: Calculation
    • TotalSubsidy = BaseSubsidy + DisabilityAddon + DependentAddon + EmergencyUplift
  8. Step 7: Lookup Table → Service_Office_Routing decision table
    • Inputs: Postcode, Program
    • Outputs: ServiceOffice, CaseworkerGroup
  9. Step 8: Subexpression (optional, for reusable logic)
    • E.g. proration for partial-month start: call Prorate_Subsidy subexpression
  10. Outputs: Eligibility, TotalSubsidy, ServiceOffice, CaseworkerGroup, IncomeCeiling (for explanation)

Setup Steps (abbreviated)

  1. Expression Sets → New
    • Name: Benefit_Eligibility_Check
    • Usage Type: Default (or select a Public Sector-specific type if available)
    • Context Definition: (optional, if reading Household/Member records via Context Service)
  2. Resource Manager: add Variables (inputs/outputs), Constants
  3. Canvas: add steps in order (Lookup Table, Conditional Group, Branch, Calculation, …)
  4. Simulate with test values:
    • Scenario 1: eligible household → check subsidy calculation
    • Scenario 2: income over ceiling → eligibility = false
    • Scenario 3: emergency uplift period → higher subsidy
    • Scenario 4: no matching decision table row → outputs stay at previous values (test!)
  5. Activate the expression set version

  2. Action: Invoke Expression Set

Decision Explainer Setup

  1. Expression Set Builder → open Benefit_Eligibility_Check V1
  2. Create Message Templates:
    • Template 1 (success): “Eligible for TotalSubsidybasedonhouseholdsize{HouseholdSize} and income below ceiling ${IncomeCeiling}.”
    • Template 2 (failure): “Not eligible: income GrossIncomeexceedsceiling{IncomeCeiling} for household size ${HouseholdSize}.”
  3. Create Expression Set Message Tokens: map step outputs to template placeholders
  4. Assign templates to steps:
    • Conditional Group (income check) → Template 2 if condition is true
    • Calculation (total subsidy) → Template 1
  5. Activate the version
  6. Run from Flow → view Decision Explainer Log History on the case record

Application filed 2026-12-01, processed 2026-12-05FY2027 (rank 1)No overlap yet
Application filed 2027-01-20, processed 2027-01-25FY2027 Emergency (rank 3)Emergency version active, highest rank wins
Application filed 2027-01-20, processed 2027-05-01FY2027 (rank 1)Emergency version ended 2027-03-31, so rank 1 applies
Application filed 2027-03-01, processed 2027-08-01FY2027 (rank 1)Caller passes EffectiveDate = 2027-03-01; rank 2 (FY2028) not yet active on that date

Key: Always pass the application’s effective date to the expression set/matrix so late processing uses the right policy.

Trade-offs Considered

OptionProsConsWhen to use
Grouped matrix for ratesAvoids repeating region column; analysts edit CSV; built-in versioning with dates + rankData lives in the matrix (a second copy); 100 MB CSV limit; 200 input sets per lookupSmall-to-medium grids where one input (the key) groups many rows
Standard matrix for ratesSimpler setup (no key/grouping)Region column repeated in every row; harder to maintainSmall grids where grouping doesn’t save much
Decision table for routingReads existing records, no duplicate data; operations ownsNeeds activation and refresh; source object must have CreatedDate + IsDeleted; expression set reads only first result from object-based tablesRules already stored as records or custom metadata
Hard-code in Apex / Flow decisionsFamiliar to developersPolicy change means deployment; opaque to auditors; no explainerTrivial, stable logic only
Custom metadata + formulasDeployable, simpleNo effective-dated versioning, no explainer, awkward for multi-input lookupsFew static values
Context Service for bulkSingle large real-time call, fast data accessNeeds context definition modeling; more complex setupThousands of records, immediate results
Batch Management for bulkScales to millions in batches; simpler than Context ServiceNot real time; nightly or scheduled onlyNightly recalculation, historical runs

Rule of thumb

  • Numbers analysts own → decision matrix (grouped if one input acts as a natural key)
  • Rules that already live as records → decision table
  • Logic that ties lookups together → expression set
  • Readable explanations → Decision Explainer

Examiner Questions & Answers

Why a decision matrix for rates and a decision table for routing? Rates are a small grid owned by analysts who edit CSVs and need dated versions. Routing rules are already records maintained by operations; a decision table reads them in place, so there’s no duplicate to sync. Trade-off: the table must be refreshed after source changes.

When would you use a standard matrix instead of a grouped matrix? If the “key” column (region) doesn’t group many rows, or if you have multiple keys (region + year), grouping adds complexity without much benefit. Grouped matrices shine when one input naturally partitions the data into several versions.

How do you handle a mid-year emergency uplift? Add a new version with a higher rank and an end date. When versions overlap, the highest rank wins; after the end date the prior version applies again. No deployment.

An application filed in March is processed in June after a policy change. Which rules apply? Pass the application’s effective date to the lookups so the version active on that date is selected. Without an effective date the default is today.

What if the decision table has no matching row? Variables keep their previous values and the step shows as executed. Initialize defaults deliberately and test the no-match path.

What happens to null outputs from a lookup? Depends on “Initialize resources to default values” (expression set setting): on, a user default (or 0) replaces null; off, null is preserved and you handle it with IsNull / IsNotNull.

The table returns several offices for one postcode. Which one is used? An expression set reading an object-based decision table takes only the first result, so design the table to return one row (or make the rule unambiguous with more input fields) rather than relying on ordering.

How do you run 120k determinations overnight? Batch Management batch job definitions invoked from Flow, keeping batch size within guardrails (watch hourly limits: 5M expression set runs, 400k decision matrix invocations, 2M standard decision table invocations); or Context Service for large single calls where real-time results matter.

How do you explain a denial to an applicant? Enable Decision Explainer on the expression set, define message templates and expression set message tokens, and show the explanation in the portal or case view. Auditors can compare runs.

Where could this design break?

  • Subexpression depth is limited to 2 levels.
  • A version can have at most 200 steps by default and 50 business elements (extensible).
  • Guest users calling rules need explicit Run Expression Sets / Run Decision Matrices permissions.
  • Decision matrices need new versions for every policy change; keep ownership clear.
  • Decision tables need manual or automated refresh after source data changes.

Build Exercise (to validate in a scratch org)

  1. Create grouped decision matrix (key = region) with household size → ceiling, base subsidy; two versions with different dates and ranks. Upload CSV or add rows manually.
  2. Create decision table on a Service_Area__c custom object (postcode, program → office, group); activate, then add a row and refresh. Watch DecisionTableActionEvent.
  3. Create expression set with Lookup Table ×2, Conditional Group, Branch, List Group + Aggregate, Calculation; simulate edge cases (no table match, null income, overlapping versions, effective date in the past).
  4. Call from a Flow and via REST; compare results.
  5. Add Decision Explainer templates and view the run history.
  6. Test versioning: create an emergency uplift version with higher rank and end date; verify it wins during the period and reverts after.
  7. Test null handling: toggle “Initialize resources to default values” and pass null income; verify behavior.
  8. Test decision table refresh: add a Service_Area__c record, run the expression set (should not see the new office), refresh the table, run again (should see it).

Not yet org-validated. Items flagged above (expression set version selection with past effective date, decision table first-result behavior, null handling) are the ones to test first.
